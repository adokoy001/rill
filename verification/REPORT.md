# rill 0.3.0の安全性検証

2026年11月21日、Linux x86_64上で実施。対象は、リダイレクトで次のリクエストを許すかを決める関数と、バッファ入力のバイト数を加算する関数、応答本文のうち書き出してよいバイト数を決める関数です。CLIとKaniが同じ `src/policy.rs` をコンパイルします。

## 定理と適用範囲

オリジンを **スキーム、ASCII小文字化したホスト、実効ポートの組**とします。HTTPの既定ポートは80、HTTPSは443です。証明には、現在と次のオリジンが等しいかを表す真偽値を渡します。URLの解析と実際の通信は結合テストで確かめました。

1. 初回はユーザー指定ヘッダーを許可する。`-H` のヘッダーを許可するかを `H`、隣り合うオリジンが等しいかを `S` とすると、許可された次の要求では `H′ = H ∧ S` となる。一度でも別オリジンを経由すると、その後は元のオリジンに戻ってもヘッダーを復活させない。
2. 許可された次の要求が本文を持つのは、現在の要求が本文を持ち、かつ応答が307または308の場合に限る。別オリジンへの遷移では、本文がある場合、または明示メソッドがGET・HEAD以外の場合は拒否する。空文字を明示的にPOSTした場合も本文ありとして扱う。301/302/303によって通常のPOSTが本文なしGETに変わる場合は追跡できる。
3. 現在がHTTPSなら、許可される次の要求もHTTPSになる。HTTPで開始して途中でHTTPSに昇格した場合にも、この性質を適用する。
4. 残り転送回数を `R` とすると、許可された遷移では自然数上で `R′ + 1 = R` が成り立つ。`R = 0` から遷移はできない。
5. `charge(used, add, limit)` が成功する必要十分条件は、自然数上で `used + add ≤ limit` が成り立つこと。成功時は正しい和を返す。検査では、任意の64ビット引数の和を128ビットの基準値と照合するため、機械整数の桁あふれを検出できる。
6. 受信予算の残りを `R`、受け取ったチャンク長を `n`、書き出してよい長さを `w` とする。任意の64ビット値について `w = min(R, n)` と `R′ + w = R` が成立する。従って最初の予算が `L` なら、任意の有限個のチャンクで書き出せる本文の総量は `L` 以下である。各チャンクで許容される先頭バイト数が最大であることも検証しており、すべての出力を抑止する実装は不合格になる。


**任意段数に対する帰納法。** 初期状態について `H₀ = true` を確認した。任意の状態と任意の入力について、受理した1遷移が上の等式を保つことを機械検証した。この2点から、受理された任意の有限経路について `Hₙ = S₁ ∧ … ∧ Sₙ` が成り立つ。HTTPSと転送回数も同じ帰納法で経路全体へ拡張できる。特定の長さまでリダイレクトを試した結果に依存しない。

## 実装への接続

`transfer.rs` は相対Locationを解決し、オリジン判定に使うホスト・スキーム・ポートをHTTPライブラリに渡すURIと照合する。HTTPライブラリの自動リダイレクトは無効。次の宛先への接続より先に `Chain::follow` が成功する必要がある。許可された状態を使い、送信箇所でヘッダーと本文を選ぶ。

`upload.rs` はバッファへ追加する前に入力バイト数を計上する。フォーム整形で取り除く改行やNUL、引数間の区切りも予算に含める。上限は8 MiBちょうど。単独の通常ファイルを `--data-binary @file` または `--json @file` で送る場合はストリーム送信する。8 MiBは入力バイトの上限であり、プロセス全体の常駐メモリとは別の量である。

`transfer.rs` はサイズが分かる応答を本文受信前に検査する。ストリームから受け取った実バイト数を `take_prefix` に渡し、許可されたスライスだけを書き出す。`output.rs` は原子的保存モードでは同じディレクトリ内の作業ファイルに書き、転送と付随出力の成功後に一度だけ差し替える。通信とファイルシステムを含む挙動は結合テストで確認した。

通常ビルドはRust 1.95.0を使用した。Kaniは専用のnightlyを使用する。Kaniもcargo-auditも実行ファイルの依存関係には含まれない。

~~~sh
# 初回の検証ツール導入
cargo install --locked kani-verifier --version 0.68.0
cargo kani setup
cargo install --locked cargo-audit --version 0.23.0

# プロジェクト直下で実行
./verification/verify.sh
~~~

`cargo audit` は実行時点のアドバイザリを取得するため、日が変わるとこの記録と異なる結果になることがある。

## 残る前提

形式証明の対象は転送許可と予算計算。URL解析器、HTTPのフレーミング、rustlsや暗号ライブラリ、DNS、OS、コンパイラ、Kani自身は信頼する構成要素である。バイナリのテストはこれらとの接続を調べる。最初からHTTPを明示した要求は平文で送る。別オリジンへの本文なしGET・HEADも許可するため、到達先IPの制限が必要なサービスでは接続先ポリシーが別途必要になる。受信量の証明は上限を指定した最終応答の本文バイトに適用する。HTTPヘッダー、TCPで受信・先読みされる総量、端末の表示、ファイルシステムのrenameと障害復旧は形式証明の外側にある。

参考資料は [Kani Rust Verifier](https://model-checking.github.io/kani/)、[HTTP Semantics §15.4](https://www.rfc-editor.org/rfc/rfc9110.html#name-redirection-3xx)、[RustSec Advisory Database](https://rustsec.org/)。
